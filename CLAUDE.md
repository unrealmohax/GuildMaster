# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Здесь — **правила работы и карта репозитория**. Описание кода игры (архитектура, сборки, конвенции) —
в `game/Assets/_Project/CLAUDE.md`, он подгружается, когда работа идёт с файлами оттуда.
Дизайн игры — в `docs/`, технические задания — в `TechJob/`.

**GuildMaster** — рабочее название: экономический симулятор гильдии авантюристов с непрямым управлением,
мрачное фэнтези без магии. Стадия — **прототип** (`docs/prototype.md`). Unity **6000.6.3f1**, URP (2D Renderer),
интерфейс — uGUI + TextMeshPro, данные — ScriptableObject, симуляция — обычный C#. Источник истины по версиям —
`game/ProjectSettings/ProjectVersion.txt` и `game/Packages/manifest.json`, а не эта строка.
Язык команды — русский; документация и тексты игры — на русском, идентификаторы кода — на английском,
коммиты — на английском или русском.

## Правила работы с кодом

**Код и контент проекта по умолчанию доступны только на чтение.** Изучать, искать, объяснять, предлагать
диффы — сколько угодно. Но `game/Assets/_Project/` (кроме песочницы), сцены, префабы, ScriptableObject'ы,
`game/ProjectSettings/` и `game/Packages/` **не меняются без явного и однозначного указания пользователя**.
«Разберись, почему падает» — это про чтение и диагноз, а не разрешение чинить. Нашёл проблему — объясни
и предложи, дальше жди решения.

**Поправка для прототипа: запущенная задача — это разрешение.** Если пользователь явно запустил задачу —
этап или пункт ТЗ из `TechJob/` («делаем этап 1», «реализуй ТЗ 11») или конкретную правку — в её рамках
можно создавать и менять код и ассеты. Рамки — то, что описано в задаче и соответствующем ТЗ. Всё, что
выходит за рамки (другая подсистема, изменение архитектуры, отступление от ТЗ), — предложить и ждать решения.
Если ТЗ противоречит дизайну или его не хватает — остановиться и спросить, а не додумывать молча.

**В коде нет ссылок на документацию** — ни номеров ТЗ и задач, ни имён документов, ни дат решений, даже в комментариях.
Комментарий описывает, что делает код, так, чтобы его можно было понять без `docs/` и `TechJob/`. Подробно —
`game/Assets/_Project/CLAUDE.md` → «Комментарии в коде».

**Рабочая площадка — `game/Assets/_Project/ClaudeSandbox/`.** Любой вспомогательный скрипт, генератор,
дамп, замерочный инструмент, черновик — создаётся там. Песочница версионируется в git.

**Перенос из песочницы в проект — отдельное прямое указание.** Инструмент, доказавший пользу, уезжает
в код проекта, в сцену или в префаб только когда об этом попросили явно.

**Коммиты и пуш — только по просьбе.**

## Работа с документацией

`docs/` — дизайн игры, `TechJob/` — технические задания на прототип. Эти папки Claude правит сам,
в рамках обсуждения с пользователем:

- **Решение пользователя записывается сразу**: в документ механики, строкой в начало `docs/decisions.md`,
  закрытием вопроса в `docs/open-questions.md`.
- **✅ — только то, что пользователь явно утвердил.** Свои предложения — 💡 (идея) или ❔ (предварительно).
  Если ответ неоднозначен — записать своё понимание и прямо сказать об этом.
- **Заменённое решение не удаляется** из `decisions.md`, а помечается ⚠️ со ссылкой на новое.
- **Изменился дизайн — поправить затронутые ТЗ** в `TechJob/` (и наоборот: противоречие, найденное в ТЗ, —
  вопрос к пользователю, а не молчаливая правка дизайна).
- Числа баланса — в `docs/content/numbers.md`; в коде — только через `BalanceSettings`.

### Правило написания ТЗ: законченная задача, ссылки только назад

- **ТЗ — законченная задача.** Его можно сделать целиком, опираясь только на уже сделанные ТЗ (с меньшим
  номером) и на `docs/`. Ссылок на механики и ТЗ, которые реализуются позже, в нём нет: ни «это будет в ТЗ NN»,
  ни заглушек «до ТЗ NN».
- **Пункт, которому нужна более поздняя фича, из ТЗ выносится.** Он делается после этой фичи: отдельным ТЗ
  или разделом «Доработка готового кода» в ТЗ самой фичи. Пример: лечение в Лазарете требует построек, поэтому
  оно не в ТЗ состояния (05), а в ТЗ построек (13).
- **Простое поведение в раннем ТЗ — полноценная функция**, а не временная подпорка. В разделе «Опирается на»
  перечислено, что из готового кода нужно этому ТЗ.
- **Номер ТЗ = порядок работы.** Новое ТЗ вставляется туда, где всё нужное ему уже сделано; если для этого
  нужна перенумерация — предложить её пользователю.
- Перед тем как отдать ТЗ — проверить поиском, что в нём нет ссылок на ТЗ с бо́льшим номером.
- Подробности и таблица старых номеров — в `TechJob/README.md` → «Как читать ТЗ».

## Git

- Стабильная ветка — `main`, рабочая — `develop` (создаётся, когда начнётся код).
- Имя ветки: `GM-XX_краткое_название` (например `GM-01_architecture`). `GM` — от GuildMaster.
- Коммит начинается с метки в квадратных скобках:
  - `[GM-XX]` — задачи кода (`[GM-01] Simulation tick loop`);
  - `[Docs]` — документация (`docs/`, `CLAUDE.md`);
  - `[TechSpec-XX]` — технические задания (`TechJob/`), `XX` — номер ТЗ (`[TechSpec-10] Requirement floor`);
    правка сразу нескольких ТЗ — диапазоном (`[TechSpec-01-17] Add GM task numbers and branch names`).
  - `[Refactor]` — правки кода вне задачи ТЗ, без изменения поведения (`[Refactor] Remove spec and doc references from code comments`).
- **Соавторство в коммитах не указывать** — без строки `Co-Authored-By`.
- Удалённый репозиторий — `origin` = `https://github.com/unrealmohax/GuildMaster.git`. Пуш — только по просьбе.

## Работа через Unity MCP

В проект подключён `com.coplaydev.unity-mcp` (HTTP-мост, `http://127.0.0.1:8080/mcp`, сервер `UnityMCP`).
Сцены и префабы (`.unity`, `.prefab`, `.asset`) правятся **через Unity Editor / MCP-инструменты**,
а не текстовым редактированием YAML.

**Скилл по самому протоколу в репозитории не лежит.** Он пользовательский (`~/.claude/skills/unity-mcp-skill`,
апстрим `github.com/CoplayDev/unity-mcp`), общий для всех Unity-проектов — не копировать его сюда и не править руками.
В `.claude/skills/` держим только знания **про эту игру**.

**MCP разрешён целиком и потому обязан быть возвратным.** Всё, что MCP трогает ради диагностики или замера,
возвращается в исходное состояние:

- **Запомни до, восстанови после.** Открытая и активная сцена, выделение, Play Mode, значения полей, которые
  крутил ради замера. В конце — вернуть как было.
- **Всё временное — удалить.** Временные камеры, объекты под замер, отладочные компоненты не переживают задачу.
- **Не сохранять сцену, если тебя не просили её менять.** Диагностика заканчивается без `SaveScene`.
- **Правки ради задачи — исключение, но объявленное.** В отчёт — список того, что изменено и что сохранено на диск.
- **Не смог вернуть — скажи прямо.**
- `execute_code` требует in-process Roslyn; в этом проекте он **не установлен**.
- После создания или правки скриптов — дождаться конца компиляции и проверить консоль на ошибки.

### ⚠️ Известные ограничения MCP (временно — разобраться)

Замечены в GM-01 (unity-mcp v10.2.0, Unity 6000.6.3f1). Причина не выяснена — вероятно, пакет не поддерживает
новый API идентификаторов объектов в Unity 6.x.

- **Ссылки на объекты сцены не ставятся.** `manage_components set_property` падает с `NotImplementedException`
  на любом свойстве; `manage_gameobject modify` с `component_properties` ставит простые поля и ссылки на ассеты
  (`{"guid": …}`), но не ссылки на объекты сцены (ни по `instanceID`, ни по имени).
  **Обход:** одноразовый Editor-скрипт в песочнице (`ClaudeSandbox/Editor/`) с `[MenuItem]` и `SerializedObject`,
  вызвать через `execute_menu_item`, проверить результат, удалить скрипт.
- **Компонент не читается** через ресурс `mcpforunity://scene/gameobject/{id}/component/{name}` — та же ошибка.
  **Обход:** сохранить сцену (если её и так меняли по задаче) и проверить YAML.
- **`read_console` по умолчанию не показывает `Debug.Log`.** С `types: ["all"]` обычные логи видны (GM-02).
  Но `Debug.LogWarning`/`LogError` с объектом-контекстом (`Debug.LogWarning(текст, ассет)`) не видны ни с каким
  фильтром — полный отчёт в таких случаях читать через вывод теста (`run_tests` с `include_details`).
- `manage_asset move` может вернуть ошибку, хотя перенос прошёл — проверять по диску и Build Settings.
- **Play Mode не крутит кадры, пока окно Unity не в фокусе** (GM-03): `runInBackground` в проекте выключен,
  `EditorApplication.QueuePlayerLoopUpdate` в Play Mode не помогает. **Обход:** GuildMaster → Sandbox → Time →
  Toggle Run In Background на время проверки; в редакторе это меняет `PlayerSettings` в памяти — выключить
  до выхода из Play Mode и сверить `ProjectSettings.asset` на диске.
- Вход в Play Mode сразу после перекомпиляции может оборваться («disconnected while awaiting command_result») —
  проверить `mcpforunity://editor/state` и повторить.

## Claude-хозяйство: `.claude/`

```
.claude/
├── skills/<name>/SKILL.md   — доменные знания по подсистемам этой игры (пока нет)
├── agents/*.md              — субагенты с ограниченным набором инструментов (пока нет)
├── settings.json            — permissions проекта (в git)
└── settings.local.json      — локальные permissions (в .gitignore)
```

- **Скилл** — готовый разбор подсистемы, сделанный в прошлых сессиях. Когда подсистема прототипа написана
  и разобрана — стоит оформить скилл, чтобы не реверсить код заново.
- **`settings.json`**:
  - `allow` — read-only bash, весь `git`, весь MCP-сервер Unity (`mcp__UnityMCP`), правка `docs/`, `TechJob/`, `CLAUDE.md`
    и песочницы;
  - `ask` — правка `game/Assets/**`, `game/ProjectSettings/**`, `game/Packages/**`. Это машинная страховка к правилу
    «код проекта только на чтение»: спросит даже в `acceptEdits`, в том числе внутри запущенной задачи.
    Правило пишется только как `Edit(path)` — оно покрывает `Edit`, `Write` и `NotebookEdit` сразу.
  - MCP под эти правила не попадает — про его дисциплину см. «Работа через Unity MCP».
- Машинно-специфичное (python, curl, пути вне репозитория) — в `settings.local.json`.

## Артефакты в репозитории

Знания и инструкции — в `.claude/`, всё, что Claude *делает*, — в песочнице
`game/Assets/_Project/ClaudeSandbox/` (её `README.md` перечисляет содержимое). Сейчас там — генератор ассетов данных (GM-02)
и меню проверки в Play Mode: время (GM-03), люди гильдии (GM-04).
