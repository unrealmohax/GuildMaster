## Цель

Каркас проекта, в котором симуляция живёт отдельно от интерфейса, идёт по часовым тактам, воспроизводима по зерну и запускается без UI.

## Проект

- **Unity 6000.6.3**, шаблон **Universal 2D (URP)**.
- Проект создаётся прямо в папке `game/` (см. [game/README.md](../game/README.md)).
- Настройки: Version Control — **Visible Meta Files**, Asset Serialization — **Force Text**. Git + Git LFS.
- Интерфейс — **uGUI** (Canvas), TextMeshPro.
- Одна сцена `Main.unity`.

### Сборки (asmdef) и зависимости

| Сборка | Зависит от | Правило |
|---|---|---|
| `GuildMaster.Data` | UnityEngine | Только определения и настройки, без логики игры |
| `GuildMaster.Core` | Data | **Без MonoBehaviour, без сцен, без `UnityEngine.Random`, без `Time`**. Из UnityEngine — только чтение ScriptableObject |
| `GuildMaster.UI` | Core, Data | Только отображение и отправка команд |
| `GuildMaster.Bootstrap` | Core, Data, UI | Создаёт симуляцию, крутит такты |
| `GuildMaster.Debugging` | Core, Data, UI | Отладочная панель, прогон без UI (Editor-меню) |
| `GuildMaster.Tests` | Core, Data | EditMode-тесты |

## Симуляция

### Основные классы

| Класс | Что делает |
|---|---|
| `Simulation` | Точка входа: хранит `WorldState`, `DataRegistry`, `RngService`, список систем. Метод `Tick()` — один игровой час |
| `WorldState` | Всё текущее состояние: время, казна, репутация, авантюристы, персонал, постройки, заказы, задания, группы, распоряжения, обращения, ленты |
| `DataRegistry` | Доступ к определениям из ScriptableObject по id |
| `RngService` | Генераторы случайных чисел с зерном (см. ниже) |
| `EventBus` | Внутренние события симуляции (`SimEvent`) |
| `CommandQueue` | Команды игрока (`ICommand`), применяются в начале такта |
| `ISimSystem` | Интерфейс систем: `void Tick(SimContext ctx)` |

### Порядок систем в такте

Каждый такт = 1 игровой час. Системы вызываются строго в этом порядке:

1. **CommandSystem** — применить команды игрока из очереди.
2. **TimeSystem** — сдвинуть время; выпустить события `HourStarted`, `DayStarted` (00:00), `MorningStarted` (06:00), `EveningStarted` (18:00), `NightStarted` (22:00), `MonthStarted` (день 1, 00:00).
3. **OrderSystem** — утром: новые заказы, снятие просроченных (ТЗ 08).
4. **QuestSystem** — продвинуть идущие задания: путь, события, раунды, возвращение (ТЗ 09).
5. **ActivitySystem** — текущие занятия людей в гильдии: сон, отдых, таверна, тренировка, лечение.
6. **StateSystem** — изменить усталость, стресс, довольство, лояльность (ТЗ 05).
7. **HealthSystem** — раз в сутки: лечение, осложнения (ТЗ 05).
8. **DecisionSystem** — решения людей в точках решения (ТЗ 06).
9. **PartySystem** — сбор групп под выбранные задания (ТЗ 07).
10. **DilemmaSystem** — проверить триггеры обращений, сроки ответа (ТЗ 13).
11. **EconomySystem** — суточные и месячные расчёты (ТЗ 10).
12. **BuildingSystem**, **StaffSystem** — стройка, найм, зарплаты (ТЗ 11).
13. **AdventurerSystem**, **RecruitSystem** — раз в сутки: пересчёт архетипа и раскрытие нейтральных осей; кандидаты в авантюристы (ТЗ 04, решение 2026-09-26).
14. **DecreeSystem** — сроки распоряжений (ТЗ 12).
15. **FeedSystem** — превратить накопленные `SimEvent` в строки лент (ТЗ 14).
16. **AutopauseSystem** — если в такте было событие с автопаузой — поднять флаг паузы (ТЗ 03).

### События симуляции

- `SimEvent` — запись: тип (`SimEventType`), время, важность, участники (id), полезные данные (словарь или типизированная структура).
- Системы **публикуют** события в `EventBus`, **FeedSystem** и **AutopauseSystem** их читают. UI подписывается на готовые строки лент и на изменения состояния.
- События очищаются в конце такта.

### Команды игрока

- Любое действие игрока — это команда (`AcceptOrderCommand`, `SetCommissionCommand`, `StartBuildingCommand`, `ToggleDecreeCommand`, `AnswerDilemmaCommand` и т.д.).
- UI **не меняет** `WorldState` напрямую — только кладёт команду в `CommandQueue`.
- Команды применяются в начале следующего такта. **На паузе** команды применяются сразу отдельным вызовом `Simulation.ApplyCommandsNow()` — игрок видит результат, не снимая паузу.

### Случайность

- Свой генератор (например, PCG32 или xorshift128+), класс `Rng`: `NextFloat()`, `Range(min, max)`, `Chance(p)`, `Pick(list)`, `PickWeighted(list, weights)`, `Normal(mean, sd)`.
- **Мастер-зерно** задаётся при старте игры (по умолчанию — случайное, показывается в отладке).
- **Отдельный поток на каждую систему**: зерно потока = хеш(мастер-зерно, имя системы). Так новая проверка в одной системе не меняет результаты других — отладка воспроизводима.
- Требование: **то же зерно + те же команды в те же такты = тот же мир**.

### Идентификаторы

- Все сущности имеют целочисленный `Id`, выдаётся `IdGenerator` в `WorldState`.
- Ссылки между сущностями — только по `Id`, не прямые ссылки объектов (упрощает отладку и будущие сохранения).

## Запуск

### В игре

- `GameRunner : MonoBehaviour` (Bootstrap) создаёт `Simulation`, строит UI, в `Update()` накапливает реальное время и вызывает `Tick()` по скорости (ТЗ 03).
- Если `AutopauseSystem` поднял флаг — `GameRunner` ставит паузу.

### Без интерфейса

- Editor-меню **GuildMaster → Run Headless…**: окно с полями «зерно», «дней», «сценарий старта»; прогоняет симуляцию максимально быстро без UI, пишет лог и сводку (ТЗ 16).
- Команды игрока в прогоне без UI — через **простого бота** (по умолчанию: принимать все заказы, комиссия 20%, ничего не строить) или по сценарию (ТЗ 16).

## Тесты (EditMode)

- Площадь перекрытия: известные фигуры → известный процент (ТЗ 09).
- Профиль группы: сумма × Слаженность (ТЗ 09).
- Архетип и ранг характеристик по формуле (ТЗ 04).
- Детерминизм: два прогона на 60 дней с одним зерном дают одинаковый лог.

## Критерии приёмки

- [ ] Проект открывается в Unity 6000.6.3, URP 2D, сборки разделены как в таблице, `GuildMaster.Core` не ссылается на UI и Bootstrap.
- [ ] `Simulation.Tick()` вызывается без сцены (в EditMode-тесте).
- [ ] Два прогона с одним зерном дают побайтно одинаковый лог.
- [ ] UI меняет мир только через команды.
- [ ] Прогон без UI на 360 дней занимает меньше минуты.
