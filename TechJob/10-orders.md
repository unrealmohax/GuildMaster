# GM-10. Заказы, доска и репутация

| Задача | Ветка | Метки коммитов |
|---|---|---|
| **GM-10** | `GM-10_orders` | `[GM-10]` — код, `[TechSpec-10]` — правки этого ТЗ |

Дизайн: [quests.md → Генерация заказов](../docs/mechanics/quests.md#генерация-заказов), [core-loop.md](../docs/core-loop.md). Числа: [numbers.md → Задания](../docs/content/numbers.md#задания), [→ Поток заказов](../docs/content/numbers.md#поток-заказов).

## Цель

Заказы появляются каждое утро, Регистратор ставит обычные на доску по правилам игрока, важные передаёт игроку. У гильдии появляется репутация, от которой зависит поток заказов и кандидатов.

## Опирается на

- GM-01: команды. GM-02: `QuestTypeDefinition`, `OrderTextTemplates`, `BalanceSettings.Orders`. GM-03: утро, дни.
- GM-04: ранги людей, шанс кандидата. GM-07: лента, падежи и род названий. GM-09: отчёт месяца.

## Репутация гильдии

- `Guild.Reputation` — float 0..100, старт — `Guild.startReputation` (5). Меняется службой `ReputationService` (изменить на Δ с причиной, в лог).
- В этом ТЗ репутация не меняется; от неё зависят количество и ранги заказов и шанс кандидата.

## Модель данных `Order`

| Поле | Что это |
|---|---|
| `Id`, `TypeId` | Охота, истребление, сопровождение, доставка |
| `Client` | Заказчик (горожанин, купец, крестьянин — из `OrderTextTemplates`) |
| `Place`, `Enemy`, `Cargo` | Место, враг, груз — из `OrderTextTemplates`, для описания и ленты |
| `Rank` | G–C |
| `Profile` | Скрытый профиль требований по 13 осям диаграммы. ✅ Хранится по всем 14 параметрам (`StatId`), у Слаженности всегда 0 — она не ось диаграммы (решение 2026-09-27) |
| `PartySizeCeiling`, `StatCeilings` | Скрытые потолки |
| `Description`, `HintStats` | Текст для игрока и людей, какие оси в нём намекнуты |
| `DescriptionAccuracy` | Скрытый множитель 0,9–1,1: насколько описание недооценивает / переоценивает задание |
| `Reward`, `Surcharge` | Награда заказчика и доплата гильдии |
| `Distance` | `Near` / `Far` |
| `ExpiresAtHours` | Когда снимут с доски |
| `Status` | `Incoming` → `OnBoard` / `AwaitingPlayer`; `Declined`, `Expired`. Список статусов расширяемый |
| `Flags` | `IsImportant`, `IsHardEarly` (сложный не по времени) |

## Генерация (каждый день в 06:00)

1. **Количество**: `1 + репутация / 10`; дробная часть — шанс ещё одного заказа.
2. **Ранг** по смеси для текущей репутации ❔:

| Репутация | G | F | E | D | C |
|---|---|---|---|---|---|
| 0–20 | 85% | 15% | — | — | — |
| 20–40 | 40% | 35% | 25% | — | — |
| 40–60 | 25% | 25% | 30% | 20% | — |
| 60+ | 15% | 20% | 25% | 25% | 15% |

   ✅ 2026-09-27 (после годового прогона): **лёгкие заказы не пропадают** — G и F есть при любой репутации. ⚠️ Было: 20–40 — G 20%, F 50%, E 30%; 40–60 — F 10%, E 50%, D 40%; 60+ — E 20%, D 50%, C 30%. С заданиями репутация за 7 недель доходила до 60, дальше приходили только D–C, а люди были G–F — гильдия простаивала.

   С шансом **5%** заказ — **сложный не по времени**: ранг +2 к выпавшему (не выше C).
3. **Тип** ❔: охота 30%, истребление 25%, сопровождение 20%, доставка 25%.
4. **Расстояние** ❔: близко 70%, далеко 30%.
5. **Профиль**: главные оси типа — `Range(главные[ранг])`, второстепенные — `Range(второстепенные[ранг])`, остальные — 0; каждая ось × `Range(0,8; 1,2)`; затем **все оси не меньше `Orders.requirementFloor` (10)**. ❔ Далеко: если Выживания нет среди осей — добавить как второстепенную.
   - Зачем порог: шанс задания считается по площади фигуры из соседних осей; без порога требуемая ось с нулевыми соседями не давала бы площади. 10 — естественный минимум параметров человека (GM-04).
6. **Потолки**: из типа. В прототипе потолков нет ни у одного типа (доставка — тоже, решение 2026-09-26), но поле остаётся.
7. **Награда**: `Range(награда[ранг])`, далеко × 1,5, округлить до 5.
8. **Срок на доске**: 3–7 дней.
9. **Описание** (ниже), `DescriptionAccuracy = Range(0,9; 1,1)`.
10. **На старте игры** ❔ — 3 заказа ранга G уже на доске.

Шаблоны профилей по типам — [quests.md](../docs/mechanics/quests.md#генерация-заказов). Генерация профиля — отдельная функция «тип + ранг → профиль».

## Описание

- Шаблон из `OrderTextTemplates` для типа: «{заказчик} просит {действие} у {место:р}».
- **Намёки** на 1–2 самые большие оси профиля (строки на каждую ось в `OrderTextTemplates.hints`):

| Ось | Пример намёка |
|---|---|
| Наблюдательность | «Говорят, зверь хитёр и осторожен» |
| Сила / Выносливость | «Их там целая стая» |
| Меткость | «Близко к нему не подойти» |
| Знания | «Никто толком не знает, что это за тварь» |
| Выживание | «Дорога идёт через глушь» |
| Реакция | «Нападает внезапно» |
| Скрытность | «Лишнего внимания не нужно» |

- Далеко — «Путь неблизкий». Задание с потолком размера — «Лишнего внимания не нужно» (в прототипе потолков нет).
- ❔ 30 строк намёков — черновик, заполняет автор.
- **Названия для ленты**: у заказчиков, мест, врагов, грузов в `OrderTextTemplates` — шесть падежных форм и род (`NounForms`, GM-07). Заполнить.

## Регистратор и важные заказы

- **Важный заказ** ❔: `IsHardEarly` или награда ≥ `importantRewardThreshold` (250).
- **Обычный заказ** Регистратор проверяет по **правилам игрока** (команда `SetRegistrarRules`):
  - какие типы брать (переключатели по 4 типам);
  - до какого ранга брать сам;
  - минимальная награда.
  Подходит → `OnBoard`. Не подходит → `Declined` (строка в ленте гильдии [О]).
- **Важный заказ** → `AwaitingPlayer`: событие [В] с автопаузой (✅ вид «Важный заказ», решение 2026-09-27), игрок **принимает** (можно сразу назначить доплату) или **отклоняет** — команда `AnswerImportantOrder(orderId, accept, surcharge)`. ❔ Без ответа 2 дня — отклонён.
- ✅ Сначала проверяется важность: важный заказ идёт игроку, даже если по правилам Регистратора он бы не прошёл. Правила — только для обычных заказов (решение 2026-09-27).

## Доска

- Игрок видит: тип, заказчик, ранг, расстояние, награда, доплата, описание, сколько осталось висеть. **Профиль не виден никогда.**
- Игрок может **назначить доплату** любому заказу на доске — команда `SetSurcharge(orderId, amount)`. Доплата — обещание: деньги из казны сейчас не списываются.
- Непопулярный заказ снимается по сроку: `Expired`. В прототипе все заказчики — горожане, последствий нет.

## Доработка готового кода

- **GM-04, шанс кандидата**: в `RecruitSystem.CandidateChance` брать `Guild.Reputation` вместо `Guild.startReputation`.
- GM-06: бот «Простой» — Регистратор берёт все типы до высшего ранга людей гильдии, без порога награды; важные заказы принимает, если в гильдии есть человек этого ранга. В лог — профиль заказа и `DescriptionAccuracy` (`Debug`). В сводку — заказов пришло / на доску / отклонено Регистратором / отклонено игроком / снято по сроку, репутация на конец месяца.
- GM-07: строки — новые заказы на доске, отклонён Регистратором, важный заказ ждёт решения, снят по сроку.
- GM-09: в отчёт месяца — раздел «Заказы»: сколько пришло, какие сняты и отклонены; раздел «Репутация»: было → стало.

## Допущения реализации (GM-10)

Решение 2026-09-27 в [decisions.md](../docs/decisions.md): вопросы перед кодом, приняты все рекомендованные варианты.

- ❔ **Репутация** — часть мира `World.Guild` (`GuildState`: `Reputation`, `StartReputation`). `ReputationService.Change(ctx, Δ, причина)` обрезает до 0..`maxReputation`, изменение — событие `ReputationChanged` (лог `Info`, без строки ленты), без изменения — ничего.
- ❔ **Заказы** — часть мира `World.Orders` (`OrderBoard`): открытые (на доске и ждущие игрока) и архив закрытых (отклонённые, снятые) не больше `Orders.closedOrdersLimit` (200), старые выбрасываются. Правила Регистратора (`RegistrarRules`), счётчики заказов за игру (`OrderTotals`, для отчёта месяца), «обещано доплат» — `GetPromisedSurcharges()` (сумма доплат на доске, не хранится). У заказов свой счётчик id: id людей не сдвигаются.
- ❔ **Скрытое** — профиль, потолки, точность описания — `internal`: снаружи симуляции не видны (тест отражением). Точность описания — `Orders.descriptionAccuracy` (0,9–1,1).
- ❔ **Система** — `OrderSystem`, шаг 3 такта, свой поток. Каждый такт — снять заказы с вышедшим сроком и отклонить важные без ответа; в начале утра (06:00) — новые заказы. Первое утро игры — второй день (игра начинается в 06:00, первый такт — 07:00); первый день закрывают стартовые заказы. Дробная часть числа заказов — бросок всегда (одно число), даже при целом числе.
- ❔ **Порядок бросков заказа**: ранг по смеси → «сложный не по времени» (бросок всегда) → тип по весам `generationWeight` → расстояние → профиль → награда → срок на доске → заказчик, место, враг, груз → шаблон описания → число намёков и намёки → точность описания. Строка смеси — последняя, у которой порог не выше репутации (20 — уже строка 20–40). «Сложный не по времени» — только если ранг вырос (выпавший C флага не получает).
- ❔ **Профиль**: значения осей из диапазона ранга — дробные, равномерно; случайный множитель — только осям шаблона (остальные — 0, их поднимает порог). Далеко и Выживания нет среди осей — Выживание второстепенной (так только у истребления).
- ❔ **Награда** — целое из диапазона ранга, далеко × 1,5, округление до 5 (половина — вверх). **Порог важного** (250) — по итоговой награде.
- ❔ **Описание** — предложения через точку: шаблон типа (метки из заказа, заглавная в начале), намёки на 1–2 самые большие оси итогового профиля (при равенстве — по порядку `StatId`), «Путь неблизкий» для дальнего, намёк на потолок размера группы. Одинаковые предложения склеиваются в одно («Их там целая стая» — намёк и на Силу, и на Выносливость). Самая большая ось почти всегда главная ось типа (тест: > 95%), но на рангах G–F второстепенная иногда её обгоняет (до 18 против 16).
- ❔ **Названия заказов** — шесть падежей и род у заказчиков, мест, врагов, грузов, вручную в генераторе (💡, правит автор); валидатор требует все шесть. В шаблонах описаний род согласуется скобкой: «объявил[ся|ась|ось|ись]@враг», «ид[ёт|ёт|ёт|ут]@груз» (телеги идут).
- ❔ **Стартовые заказы** — `OrderSystem.ApplyStart` в конструкторе симуляции после `StartScenario`, свой поток `OrderStart`: сразу на доске, без Регистратора и событий, в счётчики не входят; стартовые люди не сдвигаются (тест).
- ❔ **Правила Регистратора по умолчанию** — все типы, до ранга C, без минимума награды. Команда `SetRegistrarRules(типы | null — все, ранг, награда)`; те же правила — без события; смена — `RegistrarRulesChanged` [О].
- ❔ **Важный заказ**: ждёт ответа `playerResponseDays` × 24 часа от прихода; без ответа — `Declined` с причиной `NoAnswer`, строка [О] «{заказчик} не дождался ответа и ушёл». Отказ игрока — `Declined` / `Player`, без строки. Принят — на доске с этого часа, **срок на доске — от принятия**. Ответ на заказ, который уже не ждёт, — ничего.
- ❔ **Доплата** — целое ≥ 0, без верхнего предела, 0 снимает; только заказу на доске (и при принятии важного); та же сумма — без события; смена — `SurchargeSet` [О] без строки.
- ❔ **События** (id заказа — в данных `order`, не в участниках: участники — люди): `OrderArrived`, `OrderPosted` (`by` — registrar / player), `OrderDeclinedByRegistrar`, `OrderAwaitingPlayer` [В], `OrderDeclinedByPlayer` (`noAnswer`), `OrderExpired`, за утро — `NewOrdersPosted` и `RegistrarDeclinedOrders` (`count`). Все — `Info` (~2 тыс. строк в год при репутации 5).
- ❔ **Лента**: «Новых заказов на доске: {число}» и «Регистратор отказал заказчикам: {число}» — по строке на утро (без согласования числа); «Регистратор отложил один заказ для вас…» — [В]; «Заказ на {тип} … сняли — никто не взял» — на каждый снятый заказ, вариант по типу (в ленте появилось условие «тип задания»); строка «Регистратор принял заказ» не используется.
- ❔ **Лог** `Debug` — заказ целиком при появлении: тип, ранг, расстояние, награда, срок, важность, точность, профиль по 13 осям, потолки, намёки и текст (`order new #4 …`, стартовые — `order start`).
- ❔ **Отчёт месяца**: «Заказы» — пришло, повешено на доску, отклонено Регистратором, отклонено вами (с отказами без ответа), снято по сроку — числами, из счётчиков (разница с прошлым отчётом, поэтому предел архива отчёту не мешает); «Репутация» — «За месяц: 5 → 5». В отчёте хранятся репутация и счётчики на конец.
- ❔ **Бот «Простой»**: на каждом ходу сравнивает правила Регистратора с «все типы, до высшего ранга людей, без порога» и при расхождении шлёт команду. ✅ Важный заказ принимает без доплаты, как только в гильдии есть человек его ранга или выше; до тех пор **не отвечает** — заказ ждёт, без ответа за 2 дня заказчик уходит сам (решение 2026-09-27).
- ❔ **Сценарий**: `registrar all|none|Hunt,Escort Ранг Награда`, `answer id accept Доплата` / `answer id decline`, `surcharge id сумма`.
- ❔ **Сводка**: «Заказов пришло», «На доску», «Отклонено Регистратором», «Отклонено игроком» (с отказами без ответа), «Снято по сроку», «Репутация» (на конец месяца).

## Критерии приёмки

- [ ] Заказы появляются в 06:00 в нужном количестве и смеси рангов по репутации.
- [ ] Профиль собирается по шаблону типа, все оси не ниже порога, скрыт от игрока.
- [ ] Описание содержит намёки на главные оси.
- [ ] Регистратор ставит на доску по правилам, важные уходят игроку, без ответа — отклоняются.
- [ ] Доплата назначается командой и хранится в заказе.
- [ ] Просроченные заказы снимаются.
- [ ] Шанс кандидата зависит от текущей репутации.

## Открытые вопросы

- ❔ Смесь рангов по репутации, доли типов и расстояний, порог «важного», срок ответа игрока, стартовые заказы.
- ❔ Тексты намёков (26 строк — по 2 на ось), шаблоны описаний, падежи названий — черновик, правит автор.
- ❔ Без заданий заказы никто не берёт: почти все снимаются по сроку (прогон года, 10 зёрен: пришло ~541, на доску ~514, снято ~511, важных ~27 — все уходят без ответа: у людей нет ранга E). Сверить после заданий.
